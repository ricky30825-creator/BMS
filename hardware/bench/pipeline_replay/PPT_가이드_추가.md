# 슬라이드 ④ 리플레이에서 실시간으로 — 라이브 전환

**이미지**: `06_live_switch_ppt.svg`

## 말할 것

이 프로젝트의 데이터 경로는 세 단계를 거쳤다. **5~7월에는 가상 데이터로 파이프라인
구조만 검증**했고, **8월에는 실제로 측정한 CSV 를 재생**해 18 run 17만 표본을 흘려
넣었다. **9월에 라즈베리파이가 직접 Kafka 프로듀서가 되면서** 마지막 단계가 닫혔다.

지금은 파이가 6채널을 1초 주기로 읽어 곧바로 `battery-data` 토픽에 발행한다.
컨슈머와 PostgreSQL 은 **한 줄도 고치지 않았다** — 기록 재생과 실시간 수집이 같은
토픽·같은 스키마를 쓰기 때문이다. DB 에서는 `source` 열로만 갈린다.

## 강조할 것 — 센서 읽기 코드를 새로 짜지 않았다

이게 이 단계에서 가장 중요한 설계 판단이다. 라이브 프로듀서(`sensors_kafka.py`)의
센서 읽기 부분은 **이미 검증된 로거에서 그대로 가져왔다.**

| 채널 | 가져온 곳 | 함께 따라온 것 |
|---|---|---|
| INA226 | `ina_log.py` | `CONFIG 0x4527` · `CAL 0x0A00` · 방전 = 음수 |
| MLX90614 | `mlx_fast_log.py` | `mlx_sane()` — `0x7FFF` 스턱 리드 차단 |
| DS18B20 | `thermal_log_bulk.py` | `t=85000` 을 결측으로 처리 |

새로 짰다면 상수 하나만 어긋나도 **라이브 값과 기록 데이터가 다른 것을 재게 된다.**
같은 코드를 쓰면 그 종류의 어긋남이 원리적으로 생기지 않는다.

## 붙일 코드 — 1초 주기 발행

```python
# DS18B20 은 변환에 750 ms 가 걸려 1초 틱 안에 다른 센서와 같이 못 들어간다.
# 별도 스레드가 계속 읽고, 본 루프는 가장 최근 값을 실어 보낸다.
rec = {
    "timestamp": datetime.fromtimestamp(t).isoformat(timespec="milliseconds"),
    "voltage": round(voltage, 4),
    "current": round(current, 4),          # 방전 = 음수
    "temperature": round(surface, 2),      # max(0x5A, 0x5B)
    "soc": None,                           # 쿨롱카운팅은 run 이 끝나야 나온다
    "run_id": args.run_id,
    "elapsed_s": round(t - t0, 3),
    "source": "live",                      # ← replay 와 갈리는 유일한 지점
    "_ext": {...},
}
producer.send("battery-data", key="cell_A", value=rec)
```

## 질문 나오면 답할 것

**「왜 `soc` 가 비어 있나」** — SOC 는 전류 적산을 그 run 의 총 전하량으로 정규화한
값이라 **run 이 끝나야 계산된다.** 실시간에는 분모가 없으므로 정직하게 `NULL` 을
보낸다. 임의의 초기값을 넣으면 그 run 의 SOC 축 전체가 틀어진다.

**「기존 컨슈머를 고쳤나」** — `--live-run` 옵션 하나를 더했다. `battery_logs` 가
`runs` 를 FK 로 참조하므로 부모 행이 없으면 파이가 보낸 표본이 전부 막힌다.
적재 로직 자체는 그대로다.

# 슬라이드 ⑤ 망 이식성 — 로컬·핫스팟·클라우드가 같은 구조

**이미지**: `07_portability_ppt.svg`

## 말할 것

전 구간을 **서로 다른 사설망 두 곳에서 실제로 돌렸다.** 집 WiFi 에서 한 번,
휴대폰 핫스팟에서 한 번이다. 코드는 그대로였고 **바꾼 것은 `compose.yaml` 의
광고 주소 한 줄뿐**이다.

| | 라즈베리파이 | Kafka 브로커 | 결과 |
|---|---|---|---|
| 집 WiFi | `<LAN_IP>` | `<LAN_IP>` | 전 구간 동작 |
| 휴대폰 핫스팟 | `<LAN_IP>` | `<LAN_IP>` | 전 구간 동작 |
| AWS EC2 | 현장 망 | `<퍼블릭 IP>` | 같은 절차 |

**이것이 EC2 이전 가능성의 근거다.** 브로커가 어디 있든 무관하다는 것을 말이 아니라
실행으로 보인 것이고, 운영 전환은 같은 `compose.yaml` 에 퍼블릭 IP 를 넣는 것으로
끝난다.

## 붙일 코드

```yaml
# Kafka 는 부트스트랩 응답에 "다시 여기로 접속하라" 는 주소를 실어 보낸다.
KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:19092,PLAINTEXT_HOST://<브로커 IP>:9092
#   집 WiFi <LAN_IP>    핫스팟 <LAN_IP>    EC2 <퍼블릭 IP>
```

## 질문 나오면 답할 것

**「왜 `localhost` 로 두면 안 되나」** — 클라이언트는 부트스트랩 응답에 실린 주소로
**재접속한다.** `localhost` 로 광고하면 파이가 받아든 그 이름은 **파이 자신**을
가리키므로, 브로커를 찾아놓고도 붙지 못한다. 이 한 줄이 전부인 이유가 그것이다.

**「핫스팟에서 방화벽은 어떻게 했나」** — 아무것도 안 했다. Docker Desktop 이 만드는
인바운드 허용 규칙이 Public 프로필에 걸려 있고, 핫스팟도 Public 으로 분류되기
때문이다. 파이 탐색은 mDNS(`<HOST>`)로 했다.

# 슬라이드 ⑥ temperature 는 평균이 아니라 max(0x5A, 0x5B) 다

**이미지**: `08_hotspot_rule_ppt.svg`

## 말할 것

적외선 센서를 두 개 쓰는데, **어느 쪽이 셀을 보고 있는지가 run 마다 뒤집힌다.**
팩을 다시 놓을 때마다 겨냥이 달라지기 때문이다. 그래서 한쪽을 고정으로 정할 수 없고,
**표본마다 더 뜨거운 쪽을 취한다.**

적재된 값이 그것을 그대로 보여준다 — 두 run 의 최고온도 시점이다.

| run | 0x5A | 0x5B | 채택 | 평균이었다면 |
|---|---|---|---|---|
| `PB10000_r5_2A` (8-22) | **48.75 ℃** | 35.39 ℃ | 48.75 | 42.07 (**−6.68**) |
| `PB10000_c2_10W` (8-26) | 31.61 ℃ | **42.41 ℃** | 42.41 | 37.01 (**−5.40**) |

**부호가 뒤집혀 있다.** r5 는 `0x5A` 가 13.4℃ 높고, c2 는 `0x5B` 가 10.8℃ 높다.
개체 편차라면 방향이 유지되어야 하므로 **이것은 겨냥 차이**다. 평균을 쓰면 겨냥이
빗나가 실온을 읽고 있는 센서가 발열 신호를 절반으로 깎아 내린다.

## 함께 짚을 것 — 접촉식은 대표 온도가 못 된다

같은 시점 r5 에서 **IR 48.75℃, 접촉식 DS18B20 34.44℃ 로 14.3℃ 차이**가 난다.
케이스 표면에 붙인 접촉식은 열이 전달되는 데 시간이 걸리고 국소 핫스팟을 놓친다.
중단 온도 판정을 접촉식에 걸면 실제 표면이 훨씬 뜨거워진 뒤에야 울린다.

## 붙일 코드 — 같은 규칙을 세 겹으로

```python
def mlx_sane(raw):
    """0x7FFF 는 382.19℃ 로 환산되는 스턱 리드다. 에러 플래그가 0x8000 이라
    `raw & 0x8000` 검사를 한 비트 차이로 빠져나간다 — 실제로 6건 나왔다."""
    if raw & 0x8000 or raw == 0x7FFF:
        return None
    v = raw * 0.02 - 273.15
    return v if -40.0 <= v <= 150.0 else None

objs = [o for o in (obj_5a, obj_5b) if o is not None]
temperature = max(objs) if objs else None      # 평균이 아니다
```

```sql
-- DB 가 마지막 방어선이다
temperature REAL CHECK (temperature IS NULL OR temperature BETWEEN -40 AND 150)
```

## 질문 나오면 답할 것

**「왜 겨냥을 고정하지 않았나」** — 고정하는 것이 정답이고, 무광 검정테이프로 두 지점을
표시하는 것이 다음 작업이다. 다만 **이미 측정한 13 run 은 소급이 안 되므로**, 그
데이터를 살리는 방법이 `max()` 였다. 실제로 한 run 은 `0x5B` 가 셀을 전혀 보지
못했는데 이 규칙 덕분에 데이터가 살았다.

**「그럼 열 관련 수치는 믿을 수 있나」** — 전기 데이터는 재현성 7.1% 로 견고하지만,
**열 지표는 겨냥 오차가 지배적이라 정량 결론을 보류하고 있다.** 같은 전력에서 발열이
3.4배 차이 난 사례가 있어, 테이프로 겨냥을 고정하기 전에는 발열 지수를 산출하지 않는다.
