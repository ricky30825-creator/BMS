현재 정직한 결론은 **「세 번 모두 재현 대역 안에 들어왔다」** 까지다. 열화 추세로 말하려면 점이 더 필요하고, 가능하면 사이사이 실온을 고정해야 한다.

## 3. 실온과 발열값이 연결됐다

배터리에 붙이지 않은 온도 센서로 주변 온도를 재고, **발열값 = 표면 온도 − 실온** 을 계산하는 경로가 이번에 끝까지 뚫렸다.

```
파이 DS18B20(실온)
  → sensors_kafka_v2.py 가 temp_ambient 로 발행
  → Kafka battery-raw-metrics
  → 백엔드 consumer
  → telemetry_metric.temp_ambient  ·  battery_latest.temp_ambient
  → 대시보드 실온·발열 표시
```

### 한 일

| 단계 | 내용 |
|---|---|
| 저장소 반영 | 팀원이 계약·마이그레이션·대시보드를 구현해 둠 (4개 커밋, 47파일) |
| 마이그레이션 | `013`·`014` 적용 — 양쪽 테이블에 컬럼 생성 확인 |
| 엣지 수정 | `sensors_kafka_v2.py` 가 `temp_ambient` 를 채워 발행하도록 변경 |
| 검증 | 실측 프레임 **계약 거부 0**, DB 적재 확인 |

### 설계에서 짚을 점

실온을 **`temp_points` 밖에 둔 것**이 중요하다. 그 구조 안에는 `temp_ir_surface = max(지점들)` 이라는 불변식이 걸려 있는데, 실온은 셀 지점이 아니므로 그 최댓값 계산에 섞이면 안 된다.

백엔드의 발열값 계산은 한쪽이 없으면 **null 을 내고 대체하지 않는다.** 표면 온도로 실온을 대신하면 실온 드리프트가 「배터리가 식었다」로 조용히 둔갑하기 때문이다. 음수도 버리지 않고 남긴다 — 방이 배터리보다 따뜻한 상황 자체가 실온 프로브가 존재하는 이유다.

### 실측으로 확인된 것

run 초반 약 6분 구간에서:

| | 시작 | 5.8분 후 | 변화 |
|---|---:|---:|---:|
| IR 표면 | 25.99 ℃ | 28.19 ℃ | **+2.20** |
| 실온 | 25.44 ℃ | 25.56 ℃ | +0.12 |
| **발열값** | +0.55 | **+2.63** | — |

run 후반에는 발열값이 **+5.8 ℃** 까지 올라갔다. 실온은 거의 고정이었으므로 그 상승은 전부 부하가 만든 열이다.

## 4. 학습 입력에서 채널 하나를 물렸다

### 문제

기존 모델(v0.5)의 입력은 6채널이고 그중 하나가 **배터리 표면에 붙이는 접촉 온도**다. 그런데 보조배터리 구성(모드 2)에서는 그 센서를 쓰지 않고, **백엔드 계약도 해당 필드를 금지**하고 있다.

추론 시점에 들어오지 않는 값을 학습에 넣으면 모델이 그 채널에 기대어 학습되고, 실제로는 결측으로 들어온다. **학습 입력과 추론 입력이 달라지는 것**이고, 번들을 연결해도 이 모델은 이 시스템의 데이터를 못 받는다.

### 한 일

**같은 13 run 을 그대로 쓰되 그 채널만 빼고 다시 학습**했다. 과거 데이터는 버리지 않았다 — 8~9월 run 은 접촉 프로브가 살아 있던 시기라 6채널이 모두 있고, 학습 시점에 한 열을 내릴 뿐이다.

### 결과

> **정정 (9/29)** 처음 학습(정상창 15,434)은 `ina_part2.csv` 두 개(r1, r3b)를 빠뜨린 데이터였다. 아래는 넣고 다시 학습한 값이다. 이전 값은 6채널 결합 91.35%, 5채널 89.78% 였다.

동일 조건(13 run · 정상창 15,978 · 합성이상 3,120/3,120 · 오탐률 1% 고정):

| 모델 | 6채널 | **5채널** | 차이 |
|---|---:|---:|---:|
| LSTM-AE 단독 | 67.88% | 64.58% | −3.30%p |
| InformerLite 단독 | 90.26% | 88.40% | −1.86%p |
| **결합 (선택)** | **90.22%** | **88.43%** | **−1.79%p** |
| AUROC (결합) | 0.9691 | 0.9721 | +0.0030 |

### 읽는 법

- **AUROC 는 5채널이 오히려 약간 높다**(0.9721 대 0.9691). 문턱과 무관한 분리 능력은 줄지 않았다
- 예측 기반 InformerLite 는 −1.86%p 로, 접촉 온도에 크게 기대지 않았다
- 복원 기반 AE 는 −3.30%p 로 가장 민감했다

**1.79%p 손실은 학습·추론 불일치를 감수할 이유가 되지 못한다.** 6채널 모델은 숫자가 높아 보여도 운영에서 그 채널이 안 들어오므로 **실제 성능을 알 수 없는** 상태다. 5채널은 낮아 보여도 그 숫자를 믿을 수 있다. 다만 시드 하나로 한 번씩만 돌렸고 합성 이상 샘플도 창이 달라지면 함께 달라지므로, 이 차이가 학습 편차를 넘는지는 아직 확인하지 못했다.

> ⚠️ 두 수치 모두 **개발 단계 값**이다. 오탐률은 학습에 쓴 run 을 다시 채점한 것이고 탐지율은 합성 패턴에 대한 반응이다. 열폭주를 잡았다는 뜻이 아니고, hold-out 은 아직 안 했다. 또한 팀 README 의 v0.5 표는 보조배터리 10 run 기준이라 이쪽(13 run)과 같은 조건이 아니다 — 정확한 재현이 아니라 비슷한 수준이다.

## 5. 실측 run 을 처음 채점했다

5채널 모델로 이번 run 을 돌렸다. **학습시킨 모델이 이 시스템의 실데이터를 받은 첫 사례**다.

| 항목 | 값 |
|---|---:|
| 창 수 | 1,863 (133초 · stride 10) |
| 문턱 초과 | 17개 (**0.91%**) |
| 중앙값 | 0.0612 |
| 95 분위 | 0.3596 |
| 99 분위 | 0.9703 |
| **최고값** | **12.5550** |

### 모델이 가리킨 곳

최고점 세 창이 `t+17785` · `17795` · `17805` 에 몰려 있었다. 99분위가 0.97 인데 **약 13배로 튀어오른 값**이라 꼬리가 아니다. `ina_part2` 를 포함해 다시 학습한 5채널 모델로 채점한 값이고, 반영 전 모델에서도 같은 세 창이 최고점이었다(점수 11.8). 그 창을 채널별로 보면:

| 채널 | 최고점 창 진폭 | 평범한 창 진폭 |
|---|---:|---:|
| 전압 | 0.0025 V | 0.0037 V |
| 전류 | 0.0038 A | 0.0030 A |
| IR A | 0.46 ℃ | 0.52 ℃ |
| **IR B** | **3.74 ℃** | **0.48 ℃** |

전기 채널은 평소와 같고 **IR B 만 8배로 움직였다.** 정확한 지점을 찾으니:

```
t+17905 ~ 17906   ir_a 33.73   ir_b 33.49    <- 2초
그 외 18,801행   ir_b 는 30도 언저리 (ir_a 보다 3.5도 낮음)
```

**18,803행 중 딱 2행**이다. 5.2시간 내내 3.5℃ 벌어져 있던 두 IR 센서가 **2초 동안만 0.24℃ 차로 붙었다.** 그 순간 전압·전류는 미동도 없었다(`4.7687 V · 1.9802 A`).

### 무엇을 찾은 것인가

**`0x5B` 센서가 2초 동안 `0x5A` 와 같은 지점을 봤다.** 겨냥이 흔들렸거나 시야에 무언가 지나간 것이고, **배터리 이상이 아니라 계측 이상**이다.

| 판단 | 근거 |
|---|---|
| 모델은 작동한다 | 1,863개 창 중 가장 이상한 133초를 정확히 짚었다 |
| 찾은 것도 진짜다 | 18,803행 중 2행. 사람이 눈으로 훑어서는 못 찾는다 |
| 다만 원인은 센서다 | 그 순간 배터리에서는 아무 일도 없었다 |

이것은 1절에서 적은 **부착 검증을 건너뛴 대가**이기도 하다. 두 IR 센서가 run 내내 3.5℃ 벌어져 있었는데, 출발 전에 손으로 팩을 감싸 두 채널이 모두 반응하는지 확인했다면 미리 잡을 수 있었다. `max(5a, 5b)` 규칙 덕에 대표값은 살아 있다.

### 해석의 제약 — 이 점수가 답한 질문

선택된 v0.5 설정은 보정 범위가 `per_run` 이다. 즉 **그 run 자신의 분포로 정규화**한다. 그래서 이번 채점이 답한 질문은 이쪽이다:

| | |
|---|---|
| ✔ 답한 것 | 「이 run 안에서 튀는 구간이 있는가」 |
| ✘ 답하지 못한 것 | 「학습된 정상 대비 이 run 이 이상한가」 |

후자를 답하려면 `global` 보정이 필요하다. 그리고 여기서 **배포 경계의 제약이 하나 더 드러났다.** 코드 주석이 직접 말한다:

> `scope='global'` … can be applied to an unseen device. `scope='per_run'` fits one set per known run (**v0.5 offline selection**) and **requires the run id at scoring time.**

`per_run` 보정값은 그 run 전체의 분포(중앙값·95분위·q99)에서 나오므로 **run 이 끝나야 계산된다.** 원리상 오프라인 전용이고, 실시간 관제에는 그대로 쓸 수 없다.

## 6. 남은 것

### 시연을 못 한 이유

실시간 관제 화면은 **이상점수가 없으면 페이지를 통째로 반환하지 않는** fail-closed 구조다. 점수 없이 센서 숫자만 보이면 「이상 없음」으로 읽히기 때문이고, 설계 자체는 옳다고 본다. 화면이 *「센서 측정은 도착했지만 서버의 이상점수가 아직 산출되지 않았습니다」* 라고 어느 구간이 비었는지 짚어준다.

대신 **배터리 관리 · 추세 차트 · 이상 탐지** 화면은 열리고, 실시간 데이터는 그 내내 DB 까지 정상 적재됐다.

### 다음 단계 — 우선순위

| 순위 | 할 일 | 왜 |
|---|---|---|
| 1 | **`global` 보정으로 재선택** | 처음 보는 기기를 채점하려면 필수. 지금 설정은 원리상 오프라인 전용이다 |
| 2 | **hold-out 검정** | 이상 run 이 전부 학습에 들어가 있어 현재 수치는 개발 단계 값이다 |
| 3 | **번들 형식 연결(`adapter.py`)** | 학습 산출물과 런타임이 요구하는 형식이 달라 추론 서비스에 먼저 꽂을 수 없다 |
| 4 | **IR 겨냥 고정** | 두 센서가 3.5℃ 벌어진 채로 run 을 돌렸다. 무광 검정테이프로 지점을 고정한다 |
| 5 | **팩 물리적 라벨** | 벤치에 올린 팩을 두 번 틀리게 알고 진행했다 |

### 팀에 전달한 것

백엔드에 요청했던 두 건은 **모두 반영됐다** — 로컬 기동을 막던 compose 버그와 실온 필드. AI 쪽은 5채널 재정의가 필요하다고 근거와 함께 넘겼고, 실제로 돌려본 수치가 4절에 있다.

### 한 줄 요약

모델은 **학습도 되고 실데이터 채점도 된다.** 막힌 것은 성능이 아니라 **배포 경계** 세 군데다 — 보정 범위, 번들 형식, 그리고 입력 피처와 계약의 불일치. 세 가지 모두 원인이 특정돼 있고 해법도 정해져 있다.
