# 남은 1개월 실행 전략 (2026-08-05 확정)

브레인스토밍(2026-08-05) 결론. 회로 미조립 상태에서 남은 약 1개월을 어떻게 쓸지의 정본이다.
공모전 평가 형태: **보고서·발표자료 + 시연 영상 + 현장 라이브 시연**.

## 0. 현재 상태 (2026-08-05 기준)

| 영역 | 상태 |
|---|---|
| 부품 | ✅ 전부 도착 (2026-07-27 구매 승인분) |
| BW150 | ✅ 보유·방전 동작 확인, **WiFi판(Tuya 앱 연동 동작 확인)** |
| Raspberry Pi 5 | ✅ OS·기본 셋업 완료 |

| 회로 | ❌ 미조립 |
| 백엔드 REST/WebSocket ↔ 프론트 | ❌ 실연결 미확인 |

## 1. 핵심 판단

라이브 시연에 **릴레이 물리 차단**이 포함되는 이상 실회로 조립은 피할 수 없다.
따라서 전략은 "회로를 안 만드는 법"이 아니라 **"시연에 필요한 최소 회로를 최우선 순서로 조립"**이다.

### 기각·강등한 원안

| 원안 | 판정 | 이유 |
|---|---|---|
| 오픈 데이터(캐글 등)를 자체 수집 데이터로 제출 | **기각** | 라이브 시연과 양립 불가(릴레이 차단·실시간 계측은 재생 데이터로 재현 불가). 심사 질의(raw 로그·수집 환경 요구)에서 노출 시 실격급 리스크. 아래 §2처럼 정직한 역할이 따로 있어 불필요 |
| BW150을 메인 계측기로 | **강등 → 부하·기준기·fallback** | 텔레메트리 1초 주기라 100ms 계약·AI 윈도우(30스텝 = 3초→30초)·프론트 전면 수정이 필요 — 절약이 아니라 추가 작업. 다점 온도·압력·`age_ms` 차별점 소실. 릴레이 차단 장면은 어차피 릴레이 조립 필요 |

> **1초 주기 웹 재검증 완료(2026-08-05)**: `0xFF 0x55` 프로토콜은 1초/1회·36바이트 상태 패킷(tshaddack/dl24, syssi/esphome-atorch-dl24, sigrok 교차 확인). 폴링(0x11→0x02)·설정으로 단축 불가, 1초보다 빠르게 뽑은 사례 없음. 단 DL24 계열 캡처 기반 확인이며 BW150 직접 캡처는 아님. 공식 매뉴얼은 PC 연결을 "HID (Type-C)"로 명명 — 기존 "CH340G" 서술은 실물 확인 필요(주기 결론에는 영향 없음).

## 2. 오픈 데이터(캐글 등)의 정직한 역할

버리는 게 아니다. 출처를 명시하고 다음 용도로 쓴다:

1. **보고서**: 열폭주 전조 특성(전압 강하·온도 상승률 패턴)의 근거 자료로 인용
2. **AI 사전검증**: 모델 구조·하이퍼파라미터를 공개 데이터로 튜닝했다고 명시
3. **서사**: "공개 데이터셋으로 설계 검증 → 자체 실측 데이터로 학습" = 표준 방법론이며 심사 가점 요소

## 3. BW150의 역할 (구매 장비 활용 명분 충족)

기본 역할 3종:
- **방전 부하** — 정상 패턴 수집 사이클의 부하. 배터리엔 **CC(필요시 CR)만** — CV·CP는 매뉴얼이 배터리 사용 금지 명시
- **기준 계측기** — INA226 검증용 CSV. 4선식 배선으로 케이블 강하 없는 기준 전압 확보
- **비상 fallback** — INA226 경로가 끝내 막히면 1초 모드로 강등 시연 (에지 설계에 처음부터 포함할지 미정)

매뉴얼(BW150 User Manual)에서 발굴해 **전부 채택 확정**한 활용 7종:

| # | 기능 | 프로젝트 활용 |
|---|---|---|
| 1 | **BRT 모드** (내부저항 자동 측정) | 모드 1 셀 내부저항 실측 → 세션 메타데이터·배터리 자산 이력의 열화 지표 (Q6 모드 1에 실측 근거 제공) |
| 2 | **PT 모드** (정격/최대 출력 자동 검출) | 모드 2 빠른 진단(F21)의 "레귤레이션 이탈·스펙 도달률" 독립 교차검증. 보고서에 자체 진단 vs 상용 계측기 비교표 |
| 3 | **CT 모드** (배선 저항 측정) | 모드 2 케이블 강하 함정(28AWG 1m=800mV)을 실측 수치로 검증 |
| 4 | **외부 온도 프로브 알람** (`Over_Temp Ext.T`) | 무인 수집 중 Pi와 독립된 하드웨어 안전망 — 문턱 초과 시 BW150이 자체 부하 정지·경보 |
| 5 | **종지전압·시간제한 설정** | 무인 사이클 안전 종료 — Pi가 죽어도 과방전 없음 |
| 6 | **전압/전류 캘리브레이션 레퍼런스** | INA226 검증 기준값 품질 향상 |
| 7 | **실시간 곡선 화면** | 시연 연출 — 대시보드 옆에 기준기 화면을 배치해 수치 일치를 심사위원이 직접 확인 |

주의:
- CDC/CDCDC/CDxN 자동 사이클은 **별매 충전 제어 모듈 + 전용 충전기** 필요 → 구매하지 않는다. **릴레이 CH1(충전, Babysitter)·CH2(방전, BW150) 전환으로 대체** — 보유 부품만으로 무인 충·방전 사이클 구성
- OCP 25A·OPP 150W는 고정 문턱이라 셀 보호 대용 아님
- Pi→BW150 제어 경로: **Tuya 로컬 제어(`tinytuya`, 로컬 키 추출 필요) 1순위**, 막히면 BLE(E-test 프로토콜) → USB 시리얼 순 fallback

## 4. 주차별 계획

### 1주차: 최소 실회로 조립 + 에지 수집
- 조립: Babysitter+18650 셀 → INA226 → DS18B20×3 → MLX90614×2 → 릴레이 4ch → FSR+ADS1115 (정본: `docs/hardware/mode1_beginner_guide.md`)
- 에지 수집 코드: 100ms 루프 → `battery-raw-metrics` 발행 (`docs/hardware/mode1_backend_spec.md` 계약대로)
- H1~H9 미해결 항목(전원 넣어야 아는 것) 이 주에 소거
- **완료 기준**: 실측 JSON이 Kafka→DB까지 흐른다

### 2~3주차: 데이터 수집 + AI 실학습 + 백엔드 연결 (병행)
- **수집**: 릴레이 CH1·CH2 전환 + BW150 WiFi 제어로 **무인 충·방전 사이클** 자동화 → 정상 패턴 데이터 야간 축적
  - 무인 안전망: BW150 종지전압·시간제한 + 외부 온도 프로브 알람 (Pi와 독립)
  - 사이클 전 BRT 내부저항 측정 → 세션 메타데이터 기록. CT 배선 저항 실측 1회
  - PT 모드로 모드 2 자산 정격 검증 데이터 확보 (F21 교차검증·보고서용)
- **AI**: 축적분으로 LSTM-AE·Informer 실학습, α·β 튜닝, 이상 유도 실험(가열)으로 검증
- **백엔드**: REST/WebSocket ↔ 프론트 실연결 (`docs/backend_contract.md` 기준)
- 음성안내 MP3 생성·카카오톡 연동 마무리

### 4주차: 시연·영상·보고서
- 라이브 시연 리허설(§5), 시연 영상 촬영, 보고서·발표자료

## 5. 라이브 시연 시나리오 (전부 실동작, 안전)

1. **평시**: 셀 방전 중 → 대시보드 실시간 갱신 (100ms 계측). BW150 곡선 화면을 옆에 두어 수치 일치 확인
2. **이상점수 상승**: 셀 표면 가열(드라이기) → `dT_dt` 실제 상승 → AE 재구성 오차 증가 → 주의/경고 등급 전환
3. **릴레이 차단**: FSR 압력센서 압박(스웰링 모사) → 사후 안전계층 임계 초과 → **릴레이 즉시 차단** + 음성안내 + 카카오톡 발송
4. 위험(0.8+) 등급까지 실제 유도는 위험하므로, 필요 시 수집해둔 이상 유도 실험 데이터의 **재생 모드**(명시적 "기록 재생" 라벨)로 보완
- 서사: **3중 방어** — AI 사전 탐지 + 압력 사후 안전계층 + 기준기 독립 알람

## 6. 미확정 항목

- [ ] BW150 1초 fallback을 에지 코드 설계에 처음부터 포함할지
- [ ] BW150 동봉 외부 온도 프로브 실물 확인 (§3-④의 전제)
- [ ] BW150 PC 연결이 CH340G 시리얼인지 HID(Type-C)인지 실물 확인
- [ ] 2주 실측 데이터로 AI 학습이 충분한지 / 오픈데이터 보완 폭
- [ ] 조립 1주 완료의 현실성 (인력·납땜 경험)
- [ ] 재생 모드 필요 여부 포함 시연 세부
- [ ] 모드 2를 이번 시연 범위에서 제외할지 (제외 추천 — 회로 미설계)

## 7. 검증 기준 (주차별 통과 조건)

- 1주차 말: `battery-raw-metrics`에 실측 프레임이 100ms로 들어오는지 Kafka 콘솔로 확인
- 2주차 말: DB에 최소 수십 시간 분량의 정상 사이클 데이터 존재
- 3주차 말: 프론트가 목업이 아닌 실데이터로 렌더링, 이상 유도 시 등급 전환 확인
- 4주차: 시연 시나리오 3단계 전체 리허설 통과
