### 0-1. 배선하기 전 필독 — 단자를 잘못 고르면 사양 밖이다

**보드에 인쇄된 `input 8V<V<36V`는 부하 입력 범위가 아니다.** 제조사 사양표 기준 부하 입력은 `DC 1V~200V`이므로 18650 단일 셀(3.0~4.2V)도 보조배터리(5V)도 범위 안이다.

⚠️ **그러나 그 `8V<V<36V` 표기가 붙은 단자에 3.7V 셀을 물리면 사양 밖 동작이다.** 배선 전 부하 입력 단자(`I+` `V+` `V−` `I−` 4단자 블록)를 **정확히 식별하라.** 이건 모드 2의 5V 보조배터리에서 이미 확인한 함정과 같은 것이다.

- **BW150 자체 전원은 부하 입력과 별개다** — DC5.5 잭에 12V, 또는 CC(Type-C) 포트에 USB 5V/2A·QC/PD 12V. **전원을 안 넣으면 동작하지 않는다.**
- 배선은 **4선식(`I+`/`V+`/`V−`/`I−` 전부 결선)**을 쓴다. 2선식은 케이블 전압강하가 전압 측정에 그대로 섞인다. 우리가 재는 것이 **전압 강하 패턴**이라 이 오차는 곧 데이터 오염이다.

## 1. BW150이 주는 것 / 못 주는 것

### 1-1. 주는 것 (매뉴얼 §1·§9 화면 기준)

| 구분 | 필드 | 비고 |
|---|---|---|
| 계측 (프레임에 실림) | 전압, 전류, **누적 용량(Ah)**, **누적 에너지(Wh)**, 경과시간 | 누적값을 **기기가 적산해 준다** — 우리가 계산할 필요 없음 |
| 계측 (화면엔 있으나 프레임엔 없음) | **전력(W), 저항(Ω)** | ⚠️ `V×I`, `V/I`로 **직접 계산**해야 한다(§3-1) |
| 온도 | 외부 프로브(ETS), CPU 온도, MOSFET 온도 | 외부 프로브가 유일한 **셀 온도** 소스 |
| 상태 | 동작 모드, 부하 ON/OFF, 팬 회전수 | |
| 설정 | 방전/충전 컷오프 전압, 과전류·과전력·과온 문턱, 시간 제한, 최소 방전 전류 | 무인 수집 안전망(§7) |

## 2. AI 특징 7종 매핑 — **결론: 전부 산출 가능하다**

이 문서의 핵심 판단이다. 이상탐지 입력 특징 7종은 **BW150 단독으로 전부 만들 수 있다.**

| 특징 | BW150 출처 | 가능 | 주의 |
|---|---|---|---|
| `V_scaled` | 전압 | ✅ | 정규화는 기존 파이프라인 그대로 |
| `V_delta` | 전압 1차 차분 | ✅ | Δt가 0.1초 → **1초**로 바뀐다 |
| `V_drop` | 부하 ON 전후 전압 강하 | ⚠️ | CC ON/OFF 전환 구간에서 산출. **1초 주기라 순간 강하의 첫 과도는 놓친다** — 정상상태 강하만 잡힌다 |
| `I_smooth` | 전류 | ✅ | 1초 값이라 이미 평활된 셈 |
| `dT_dt` | 외부 프로브 온도 1차 차분 | ✅ | **1점 온도**라 국부 피크는 못 잡는다 |
| `d2T_dt2` | 외부 프로브 온도 2차 차분 | ⚠️ | 프로브 분해능·1초 주기에서 노이즈가 커진다 → 평활 창 필요 |
| `Wh_cumsum` | 누적 에너지(Wh) | ✅ | **기기가 직접 적산** — 우리가 계산할 필요 없음 |

### 2-1. 대가로 잃는 것

- **윈도우 시간이 10배로 늘어난다.** 30 time-steps가 3초 → **30초**. 모델 구조는 그대로지만 **"30스텝이 무슨 시간을 덮는가"의 의미가 달라지므로**, 조립 후 100ms 데이터와 같은 모델에 섞어 넣으면 안 된다(§8-1).
- **공간 온도차 특징이 사라진다.** 다점 온도(`temp_points`)로 쓰려던 지점 간 온도차는 프로브 1개로 불가능하다.
- **압력 기반 사후 안전계층 데이터가 없다.**

> **그렇지만 1초가 이 프로젝트의 진짜 약점은 아니다.** 문헌상 우리 센서 구성으로 겨냥할 수 있는 건 애초에 "폭주 직전 초 단위 신호"가 아니라 **분~시간 단위로 벌어지는 이탈**이다. 근거와 함의는 §5-0에 정리했다 — **수집을 시작하기 전에 반드시 읽어라.**

### 2-2. `soc_pct` 대체 — 모드 2와 같은 방식

BQ27441이 없으므로 **적산 상대 SOC**를 쓴다. 모드 2에서 이미 확정한 방식과 동일하다:

```
soc_pct = 100 × (1 − 누적방전_mAh / 정격_mAh)
```

만충 상태에서 시작하는 것을 전제로 하며, 누적 mAh는 BW150이 직접 준다.
**절대 SOC가 아니다** — 모드 1의 BQ27441 `soc_pct`와 같은 값으로 취급하면 안 된다.

## 3. 추출 경로 — **BLE를 쓴다**

### 3-0. 결론 먼저

**2026-08-06 실물 확인으로 결론이 바뀌었다. BLE가 유일하게 동작하는 경로다.**

| 경로 | 실측 결과 | 평가 |
|---|---|---|
| **① BLE (채택)** | ✅ **36바이트 `FF 55` 프레임이 초당 1개씩 흐른다** | **주력.** §3-2 |
| ② USB HID | ❌ 장치는 열리고 write도 되는데 **입력 리포트가 0개**. 알려진 깨우기 명령에도 무응답 | 막힘. §3-1a |
| ③ Tuya WiFi (tinytuya) | 미시도 | 수집엔 부적합(아래), 제어·원격 감시용 |
| ④ PC 소프트웨어 XLS | ❌ **Windows 전용이라 맥에서 불가** | — |
| ⑤ 화면 수동 기록 | 가능 | 최후 수단 (기존 스펙 §13 H7이 허용) |

**Tuya를 수집에 안 쓰는 이유**(경로가 살아 있어도 마찬가지):
- tinytuya는 **1초 미만 폴링을 권고하지 않고**, 전력 계측류는 5~10초가 커뮤니티 권장이다. 너무 자주 부르면 기기가 연결을 끊는 사례가 보고된다.
- 로컬 키를 얻으려면 Tuya IoT Platform Cloud 프로젝트가 필요하고 **트라이얼이 1개월 단위**라 만료되면 수집이 멈춘다. 남은 기간이 1개월인 지금 순수한 리스크다.

> ### ⚠️ "USB 절연 없음" 문제는 이제 무관하다
> 기존 스펙이 경고한 건 *"BW150 USB를 꽂으면 측정 회로와 GND가 묶인다"*였다. **BLE로 가면 애초에 전기적으로 안 묶인다** — 조립 후 INA226·Pi와 함께 써도 이 문제가 없다. 결과적으로 HID가 막힌 게 손해만은 아니다.

### 3-1a. 컴퓨터에 물리적으로 연결하기

#### 포트가 두 개다 — 헷갈리면 아무것도 안 잡힌다

| 포트 | 용도 | 주의 |
|---|---|---|
| **DC5.5 잭** 또는 **CC(Type-C) 포트** | **BW150 자체 전원** | DC5.5는 12V, CC는 USB 5V/2A 또는 QC/PD 12V |
| **HID computer online 포트** | **PC 데이터 연결** | 위 전원 포트와 **다른 포트다** |

**BW150은 전원을 따로 넣지 않으면 동작하지 않는다.** 매뉴얼이 "전원 어댑터는 미포함"이라고 명시하고 있으니, 화면이 켜지는 것부터 확인하고 데이터 케이블을 꽂아라.

#### 연결 순서

1. **전원을 먼저 넣는다** — 화면이 켜지는지 확인
2. **동봉된 `Computer Online cable`로 HID 포트와 PC를 연결한다**
   ⚠️ 아무 USB 케이블이나 쓰면 안 된다. 충전 전용 케이블은 데이터 선이 없어 장치가 안 잡힌다.
3. 포트가 잡혔는지 확인:

```bash
python3 edge/bw150/detect.py
```

#### ✅ B4 확정 — CH340G 시리얼이 아니라 **USB HID**다 (2026-08-06 실물 확인)

실물을 연결해 확인한 결과다. **기존 문서의 "CH340G" 전제는 틀렸다.**

| 항목 | 실측값 |
|---|---|
| 제품 문자열 | `ATORCH BW150 V1.1.0` (제조사 `APP`) |
| VID / PID | **`0x0483` / `0x5750`** — STMicroelectronics. STM32 내장 USB이지 USB-시리얼 변환칩이 아니다 |
| 인터페이스 | USB HID, 벤더 정의 usage page **`0xFF02`**, usage `0x02` |
| 리포트 | 입력·출력 각각 **64바이트**, **리포트 ID 없음** |
| 리포트 디스크립터 | `06 02 FF 09 02 A1 01 09 03 15 00 26 FF 00 75 08 95 40 81 00 09 04 15 00 26 FF 00 75 08 95 40 91 00 C0` |

**결과적으로 `/dev/cu.*` 시리얼 포트는 절대 생기지 않는다.** `pyserial`이 아니라 **`hidapi`**를 쓴다.

```bash
pip install hidapi
```

- 리포트 ID가 없으므로 **macOS hidapi로 쓸 때 앞에 `0x00` 바이트를 붙여야 한다**(64바이트 페이로드 + 1 = 65바이트 write).
- `get_input_report`·`get_feature_report`는 **지원하지 않는다**(read error). 인터럽트 IN 리포트만 온다.
- **ATORCH 공식 PC 소프트웨어는 Windows 전용이다**(매뉴얼 FAQ: Win7/Win10 이상). 맥에서는 못 쓰므로 §3-4의 자체 스크립트가 선택이 아니라 필수다.
- 장치가 안 보이면: `ioreg -p IOUSB -w0 -l | grep -i 'product name'`
  (`system_profiler SPUSBDataType`는 환경에 따라 출력이 비어 나올 수 있다.)

> **HID라는 사실이 프로토콜 자체를 바꾸지는 않는다.** `FF 55` 프레임은 64바이트 HID 리포트 안에 실려 오는 것으로 보이며, 파서는 그대로 쓴다. 다만 **PX-100 제어 명령이 HID 경로에서도 통하는지는 별도 확인이 필요하다**(§9 B3).

#### 🚨 macOS Input Monitoring 권한 — 이걸 모르면 몇 시간을 날린다

**증상이 "기기가 데이터를 안 보낸다"와 완벽하게 똑같다.** 실제로 여기서 한 번 막혔다(2026-08-06).

| 동작 | 권한 거부 상태에서 |
|---|---|
| `hid.enumerate()` | ✅ 장치가 보인다 |
| `open()` | ✅ 성공한다 |
| `write()` | ✅ 성공한다 (출력 리포트는 권한이 필요 없다) |
| **`read()`** | ❌ **조용히 아무것도 안 온다** — 오류도 안 난다 |
| `get_input_report()` | ❌ read error |

즉 **입력만 막히고 나머지는 다 정상으로 보인다.** 기기 설정을 아무리 만져도 안 풀린다.

**확인**:

```bash
python3 edge/bw150/detect.py      # 권한 상태를 함께 출력한다
```

내부적으로 `IOKit`의 `IOHIDCheckAccess(kIOHIDRequestTypeListenEvent)`를 호출한다 — `0`=허용, `1`=거부, `2`=미결정.

**해결**: 시스템 설정 → 개인정보 보호 및 보안 → **입력 모니터링**에서 **명령을 실행하는 앱**을 켜고 **그 앱을 완전히 종료 후 재실행**한다.

> ⚠️ **권한 대상은 파이썬이 아니라 그 파이썬을 띄운 GUI 앱이다.** 터미널에서 직접 돌리면 Terminal.app/iTerm, 다른 도구 안에서 돌리면 그 도구의 `.app`이다. `detect.py`가 실제 호스트 앱 이름을 찾아 알려준다.
>
> ⚠️ **한 번 거부되면 macOS가 다시 묻지 않는다.** 프로그램에서 `IOHIDRequestAccess`를 불러도 대화상자가 안 뜨므로 반드시 손으로 설정에 들어가야 한다.

#### 확인 스크립트

```bash
# 1) 장치 확인 (HID 열거)
python3 edge/bw150/detect.py

# 2) 입력 리포트 읽기 — B1(디바이스 타입)·체크섬을 자동 판정한다
python3 edge/bw150/detect.py --read

# 3) 파싱이 실패하면 리포트 원본 hex 보기
python3 edge/bw150/detect.py --read --raw

# 4) 리포트가 안 오면 깨우기 명령 시험 (리셋·버튼 명령은 제외돼 있다)
python3 edge/bw150/detect.py --probe
```

의존성은 `hidapi` 하나다(`pip install hidapi`).

### 3-1. ① 유선 시리얼 — 프로토콜 명세

**핵심: 방향에 따라 서로 다른 프로토콜 두 개를 쓴다.**

| 방향 | 프로토콜 | 용도 |
|---|---|---|
| 기기 → PC | **Atorch 네이티브** `FF 55 01 …` (36바이트) | 1초 주기 상태 **자동 push** |
| PC → 기기 | **PX-100 레거시** `B1 B2 <cmd> <d1> <d2> B6` (6바이트) | 부하 ON/OFF, 전류·컷오프 설정 |

**시리얼 파라미터: 9600bps, 8N1, 흐름제어 없음.**

#### 상태 프레임(type `0x01`, DC 타입) 바이트 레이아웃

| 오프셋 | 길이 | 필드 | 스케일 |
|---|---|---|---|
| 0-1 | 2 | 매직 헤더 `FF 55` | — |
| 2 | 1 | 메시지 타입 (`01`=리포트) | — |
| 3 | 1 | 디바이스 타입 (`02`=DC 추정) | — |
| 4-6 | 3 | **전압** | 24bit BE × 0.1 → V |
| 7-9 | 3 | **전류** | 24bit BE × 0.001 → A |
| 10-12 | 3 | **누적 용량** | 24bit BE × 0.01 → Ah |
| 13-16 | 4 | **누적 에너지** | 32bit BE × 10 → Wh |
| 24-25 | 2 | **온도** | 16bit BE, raw °C |
| 26-27 | 2 | 경과 시(hour) | 16bit BE |
| 28 / 29 | 1 / 1 | 경과 분 / 초 | raw |
| 30 | 1 | 백라이트 설정 | raw |
| 35 | 1 | 체크섬 | 아래 |

#### ⚠️ 반드시 알아야 할 함정 3가지

1. **전력(W)은 프레임에 없다.** `power_w = voltage_v × current_a`로 **직접 계산**해야 한다. 저항도 마찬가지(`V/I`).
2. **오프셋 10-12는 "Watt"가 아니라 누적 용량(Ah)이다.** 일부 공개 문서가 이 자리를 전력으로 적어 두었으나, 실측 샘플로 검증하면 순간 전력과 전혀 맞지 않는다(28.2V × 0.06A = 1.69W인데 "Watt" 해석은 123.6W). **문서를 그대로 믿지 말고 첫 프레임에서 직접 확인하라.**
3. **디바이스 타입 바이트가 `02`인지 실기로 확인해야 한다.** DC 부하이므로 `02`가 유력하나 BW150 직접 캡처 근거는 없다. 첫 연결 시 3번째 바이트를 찍어 보고 다르면 파서를 맞춘다.

#### 체크섬

```python
def atorch_checksum(payload: bytes) -> int:
    """payload = frame[2:-1] — 매직헤더와 체크섬 바이트를 뺀 나머지 전부"""
    return (sum(payload) & 0xFF) ^ 0x44

def verify(frame: bytes) -> bool:
    return atorch_checksum(frame[2:-1]) == frame[-1]
```

#### 제어 명령 (PX-100, 6바이트, 체크섬 없음)

```
[0xB1][0xB2][CMD][D1][D2][0xB6]     → 응답 ACK 단일 바이트 0x6F
```

| CMD | 동작 | D1, D2 |
|---|---|---|
| `0x01` | 부하 ON/OFF | D1=`01`/`00`, D2=`00` |
| `0x02` | **정전류 설정** | D1=정수부, D2=소수부×100 (1.23A → `01 17`) |
| `0x03` | 컷오프 전압 설정 | 동일 인코딩 |
| `0x04` | 타임아웃(초) | D1D2 = 16bit unsigned |
| `0x05` | 카운터 리셋 | `00 00` |

> **PX-100 명령이 BW150에서 통하는지는 실기 검증이 필요하다.** DL24/DL24P에서는 확인됐지만 BW150 직접 캡처 근거가 없다. **가장 먼저 할 일: `0x01` ON 명령을 보내고 `0x6F`가 오는지 확인.** 안 되면 제어는 본체 버튼/Tuya로 하고 시리얼은 읽기 전용으로 쓴다 — **수집 자체는 읽기만으로 성립한다.**

### 3-2. ② BLE — ✅ **실제로 동작하는 유일한 경로다** (2026-08-06 실측)

**USB HID는 입력 리포트가 흐르지 않아 막혔고(§3-1a), BLE는 바로 됐다.** 현재 수집 주력은 BLE다.

| 항목 | 실측값 |
|---|---|
| 광고 이름 | **`BW150_BLE`** |
| Service | `0000ffe0-0000-1000-8000-00805f9b34fb` ✅ |
| **Notify(수신)** | `0000ffe1-…` — `notify` + `write` + `write-without-response` |
| Write(명령) | `0000ffe2-…` — `write` + `write-without-response` |
| 그 밖의 서비스 | `0000ae30`(ae01/ae03 write, ae02/ae04 notify, ae05 indicate, ae10 read/write), `0000ae3a` — 범용 BLE 모듈 계열로 보이며 데이터는 안 나온다 |
| 프레임 | **36바이트 `FF 55 01 02 …`, 약 1초에 1개** |

```bash
pip install bleak
python3 edge/bw150/ble_probe.py --scan     # 장치 찾기
python3 edge/bw150/ble_probe.py --watch    # 실시간 + 변하는 바이트 표시
```

> ⚠️ **스마트폰 앱(Tuya/E-test)이 물고 있으면 맥이 못 붙는다.** 앱 연결을 먼저 끊을 것.
> ⚠️ 신호가 약하면(rssi < −85) 연결이 자주 끊긴다. 기기를 맥 가까이 둔다.

#### 🚨 공개 문서의 바이트 레이아웃·체크섬이 이 기기에서 **맞지 않는다**

실측 프레임(부하 OFF, 보조배터리 연결):

```
ff 55 01 02 00 00 30 00 03 e8 00 00 12 00 00 00 00 00 00 64
00 00 00 00 00 23 00 00 03 27 3c 00 00 00 00 23
```

| 확인된 것 | 내용 |
|---|---|
| ✅ 매직 헤더 `FF 55`, 타입 `01` | 문서와 일치 |
| ✅ **B1 — 디바이스 타입 `0x02`(DC)** | 문서와 일치. **닫힘** |
| ✅ 길이 36바이트, 주기 약 1초 | 문서와 일치 |
| ❌ **체크섬** | 문서의 `(sum(frame[2:-1]) & 0xFF) ^ 0x44`가 **안 맞는다**. 게다가 데이터가 변해도 `[35]`가 그대로라 **`[35]`는 체크섬이 아니다** |
| ❓ 필드 오프셋 | 미검증. 부하 OFF 상태라 변하는 바이트가 `[9]` 하나뿐이라 특정 불가 |

#### 🚨 **BLE 프레임에 화면 값의 절반이 없다** (2026-08-06 실측)

CC 1.000A 방전 중, 화면과 프레임을 동시에 대조한 결과다.

**화면**: `Vol 004.851V · Cur 001.000A · Pwr 0004.85W · Res 0004.85Ω · Ene 1.26730Wh · Cap 000232mAh · 000:12:34 · CPU 31.0℃ · MOS 35.5℃ · ETS Wait · Fan 1020RPM · Is=01.0000A`

**프레임**: `ff 55 01 02 | 00 00 30 | 00 03 e7 | 00 00 10 | 00 00 00 00 | 00 00 64 | 00 00 00 00 | 00 23 | 00 00 00 00 | 3c | 00 00 00 00 | 23`

| 위치 | 값 | 해석 |
|---|---|---|
| `[7:10]` | 999~1000 | ✅ **전류 1.000A (×0.001)** — CC 리플까지 보인다. 확정 |
| `[4:7]` | 48 | ❓ **전압(4.8)·전력(4.85)·저항(4.85) 중 어느 것인지 못 가린다** — 전류가 정확히 1.000A라 셋이 우연히 같은 숫자다 |
| `[10:13]` | 천천히 증가 | ❓ 누적값으로 보이나 화면 `Cap`·`Ene` 어느 쪽과도 절대값이 안 맞는다 |
| `[17:20]` | 100 | ❓ `Is` 설정(1.00A ×100) 또는 과온 설정(100℃) |
| `[25]`, `[35]` | 35, 35 | ❓ MOS 온도(35.5) 추정. 같은 값이 두 자리에 |
| `[30]` | 60 | ❓ 백라이트 초 추정 |

**45초 연속 관측에서 변하는 바이트는 `[9]`와 `[12]` 둘뿐이었다.** 1A 방전 중이면 `Cap`은 +13mAh, `Ene`는 +0.06Wh, 경과시간은 +45초여야 하는데 **어느 바이트에도 나타나지 않는다.**

`ffe1`·`ffe2`에 조회 명령(PX-100 `0x10`/`0x11`/`0x14`/`0x15`, Atorch `FF5511`)을 써 봐도 **프레임이 달라지지 않는다.**

> **매뉴얼이 이 상황을 예고하고 있었다.** FAQ에 *"이 블루투스 앱 버전은 스위치 제어용일 뿐이며 주 측정용이 아니다. 측정에는 PC 소프트웨어를 쓰라"*고 적혀 있다. 즉 **BLE 프레임이 축약된 것은 사양일 가능성이 높다.**

#### ⚠️ 결정적 계산 — BLE는 **분해능이 부족해서** 어차피 못 쓴다

`[4:7]`이 전압·전력·저항 중 무엇이든 **전압은 복원할 수 있다.** 전류를 이미 알기 때문이다:
`P = V×I`, `R = V/I` → 전력이면 `V = P/I`, 저항이면 `V = R×I`. 누적 에너지도 1초마다 `V×I`를 적분하면 되고, 상대 SOC도 전류 적분으로 낸다. **즉 필드 정체를 몰라도 값은 나온다.**

**문제는 분해능이다.** 화면이 `4.851V`인데 프레임은 `48`이다 → **스케일이 ×0.1, 즉 0.1 단위**다. 셋 중 무엇이든 마찬가지다.

| | 화면 | BLE 프레임 |
|---|---|---|
| 전압 표시 | `004.851 V` (1mV) | `48` → **4.8V (0.1V)** |

**0.1V 분해능이면 리튬이온 셀 전 구간(3.0~4.2V)이 고작 12단계다.** `V_delta`(1초 전압 차분)는 거의 항상 0이 되고 가끔 1단계씩 튀는 계단 파형이 된다 — **`V_scaled`·`V_delta`·`V_drop` 세 특징이 사실상 무의미해진다.** 이건 필드 정체를 밝힌다고 해결되는 문제가 아니다.

> **그래서 `0.5A로 바꿔 필드를 특정하는 실험`은 더 이상 결정적이지 않다.** 정체를 밝혀도 분해능이 그대로다. **BLE는 제어·보조 감시용으로 격하하고, 데이터 수집 경로는 다시 골라야 한다**(§3-5).

**그래서 파서를 문서대로 확정하면 안 된다.** `ble_probe.py`로 **조건을 바꿔가며 캡처해 실측으로 필드를 알아내는 것**이 지금 할 일이다(§9 B16).

```bash
# 조건별로 캡처하고 --note 에 반드시 조건을 적는다
python3 edge/bw150/ble_probe.py --capture 60 --out idle.jsonl --note "부하 OFF"
python3 edge/bw150/ble_probe.py --capture 60 --out cc05.jsonl --note "CC 0.5A 방전"
python3 edge/bw150/ble_probe.py --capture 60 --out cc10.jsonl --note "CC 1.0A 방전"

# 캡처들을 비교하면 그 조건에 반응하는 바이트가 드러난다
python3 edge/bw150/ble_probe.py --analyze idle.jsonl cc05.jsonl cc10.jsonl
```

### 3-3. ③ Tuya WiFi — 제어·원격 감시 전용

수집 주력으로는 쓰지 않되, **원격에서 부하를 끄거나 상태를 확인**하는 데는 유용하다.

절차: Tuya IoT Platform에 Cloud 프로젝트(**Development Method는 "Smart Home"**) 생성 → Smart Life 앱 계정 연결(QR) → `python -m tinytuya wizard`로 로컬 키 확보 → `python -m tinytuya scan`으로 IP·프로토콜 버전 확인.

> **트라이얼 만료 주의**: IoT Core 구독이 처음 1개월만 유효하고, 만료되면 wizard가 `28841002` 오류로 막힌다. 무료 연장 신청(1/3/6개월, 승인 1~2영업일)이 가능하나 **수집 일정에 이걸 끼워 넣지 마라.**
> 개발자 계정 없이 로컬 키를 얻는 우회 도구(`vineetchoudhary/tuya-local-key`, QR 로그인 방식)가 2026-08 기준 동작 보고가 있다.

#### DP(데이터포인트) 맵

BW150을 ESP8266으로 개조한 공개 프로젝트(`1RandomDev/atorch-bw150-esphome`)에서 역공학된 표다. **stock Tuya 모듈에서 같은 번호가 나올 가능성이 높지만 직접 검증된 것은 아니다** — `d.status()`의 `dps` 딕셔너리와 대조하라.

| DP | 의미 | 스케일 | R/W |
|---|---|---|---|
| 101 / 102 / 103 | 전압 / 전류 / 전력 | `/100` / `/1000` / `/100` | R |
| 104 | **부하 ON/OFF** | bool | R/W |
| 105 / 106 | 용량(mAh) / 에너지(Wh) | — / `×100` | R |
| 108 | **동작 모드** | enum 0–8 (⚠️ 각 값 ↔ CC/CR/BRT 대응은 미확인) | R/W |
| 109 | **설정값**(전류·전압 등) | `/100` | R/W |
| 110 | 제한 시간 | `/100` h | R/W |
| 111 / 112 | 충전 / 방전 컷오프 전압 | `/100` | R/W |

### 3-5. 남은 경로와 권고 (2026-08-06 시점)

세 경로를 다 시험한 뒤의 상태다.

| 경로 | 상태 | 분해능 | 판정 |
|---|---|---|---|
| USB HID | ❌ **완전 침묵.** 권한 허용·부하 가동 중에도 입력 리포트 0개. 루프백조차 없다. 알려진 명령·단일바이트·프레임 에코백 전부 무응답 | — | **보류.** 공개 역공학 자료가 없어 Windows에서 공식 SW를 USBPcap으로 캡처해야 풀린다 |
| BLE | ⚠️ 동작하지만 **축약 프레임** — 전류만 온전, 나머지는 0.1 단위 | 전압 **0.1V** | **제어·보조 감시용으로 격하** |
| **Tuya WiFi** | 미시도. 사용자 앱 연동은 확인됨 | 전압 **0.01V**(DP 101 `/100`), 전류 1mA(DP 102 `/1000`) | **다음 후보** |
| Windows + 공식 SW | 미시도 | 화면과 동일(1mV) | **가장 확실하나 Windows 필요** |

**권고 순서**

1. **Tuya 로컬(tinytuya)을 먼저 시험한다.** 전압 0.01V면 셀 구간(3.0~4.2V)이 120단계라 평활을 걸면 `V_delta`가 성립한다. 이미 앱 연동이 되는 상태라 진입 비용이 가장 낮다. 폴링 1초가 실제로 견디는지, DP 번호가 §3-3 표와 맞는지 확인이 관건이다(§9 B7·B18).
2. **그래도 안 되면 Windows + 공식 소프트웨어.** XLS를 1초 간격으로 내보내 CSV로 변환한다. 자동화는 안 되지만 **분해능은 화면과 동일**하고, 덤으로 USBPcap으로 HID 핸드셰이크를 캡처해 두면 나중에 맥에서 직접 읽는 길도 열린다.
3. BLE는 어느 쪽으로 가든 **부하 ON/OFF 원격 제어와 전류 감시**에 계속 쓴다 — 전류만큼은 1mA로 정확하다.

> ⚠️ **회로 조립이 끝나면 이 문제 자체가 사라진다.** 전압·전류는 INA226이 100ms·mV급으로 주고, 온도는 DS18B20·MLX90614가 준다. **BW150 단독 수집은 어디까지나 조립 전 임시 조치이므로, 여기에 시간을 더 쓰기보다 조립을 앞당기는 편이 나을 수 있다**(`docs/final_month_strategy.md` §4 1주차).

## 4. 충전 경로 — BW150은 방전 전용이다

**BW150은 전자부하다. 충전을 못 한다.** 사이클 데이터를 만들려면 충전 수단이 따로 필요하다.

| 방법 | 내용 | 비고 |
|---|---|---|
| **(권장) Babysitter 최소 결선** | USB 5V → `VIN`, 셀 → JST(`BAT+`/`BAT−`). 전체 회로 없이 이것만으로 충전기가 된다 | 슬라이드 `S1`=`ON`, DIP `EN1`만 ON(`EN2=1,EN1=0`) → `I_CHG ≈ 1.5A`. **2550mAh에 0.59C이므로 셀 데이터시트 확인 필수** |
| 별도 18650 충전기 | 시판 충전기 사용 | 충전 곡선 데이터는 못 남는다 |

- **충전 중 데이터도 남기려면** BW150을 떼고 Babysitter로 충전하는 동안은 계측이 끊긴다. 릴레이(CH1/CH2) 없이는 **수동 전환**이며, 이것이 조립 전 무인 사이클의 한계다.
- 따라서 **조립 전 수집의 주력은 "방전 곡선"**이고, 충전 구간은 조립 후에 채운다.

> ⚠️ **CDC/CDCDC/CDxN 자동 충방전 사이클 모드는 별매 충전 제어 모듈 + 전용 충전기가 필요하다.** 구매하지 않기로 했으므로 이 모드들은 쓸 수 없다.

## 5. 시험 프로토콜

### 5-0. ⚠️ 먼저 알아야 할 현실 — 병목은 1초가 아니라 센서 채널이다

문헌을 뒤진 결과, **1초 샘플링이 이 프로젝트의 진짜 약점이 아니다.**

- 열폭주 최종 단계는 **1°C/s** 수준이라 1초로도 잡힌다. 전이 구간은 **10°C/min(≈0.17°C/s)**, 자기발열 시작은 **1°C/min**이다.
- 가장 이른 전조는 **가스**다 — 과충전 시작 후 DMC 약 390초, CO 약 482초에 검출되어 전압·온도보다 10분 이상 앞선다. **모드 1엔 가스 센서가 없다**(온도 오염 때문에 일부러 뺐다). 이건 조립을 해도 안 생긴다.
- 온도 기반 탐지는 통상 임계 실패 **30~60초 전**에야 반응한다.

**그래서 AI가 겨냥해야 할 것은 "폭주 직전 초 단위 신호"가 아니라 분~시간 단위로 서서히 벌어지는 이탈**이다 — 온도 기울기의 지속 상승, 내부저항 추세 이탈, 전압 회복 지연. **이 시간 스케일에서는 1초 샘플링이 충분하다.**

> 다만 `1°C/min`처럼 완만한 조기 신호는 60샘플 이상을 봐야 해서 노이즈에 묻히기 쉽다. `dT_dt`·`d2T_dt2`에 **이동평균 평활을 반드시 걸어라.**

### 5-1. 시험 매트릭스

셀 자산: 18650 2550mAh ×3, 리튬폴리머 1000mAh ×2. **1개는 "열화 셀"로 전용**한다(5-3 참조).

### 5-2. T3(정상패턴 다양화)를 왜 최우선으로 두는가

- AutoEncoder는 **정상 분포를 배우고 그로부터의 이탈을 탐지**한다. 정상 데이터의 **양보다 다양성**이 중요하다.
- 한 사례 연구에서 **정상 24시간**만으로 LSTM-AE가 유의미한 성능을 냈다. 수십 시간이면 현실적 목표다.
- 전류를 5~10분마다 바꾸는 건 NASA Randomized Battery Usage 데이터셋의 방식을 모사한 것이다(그쪽은 5분마다 0.5~4A 무작위 재선택).
- **자동화 방법**: PX-100 `0x02`(전류 설정) 명령을 스크립트로 주기 전송하면 무인으로 돌아간다. B3(§9)가 통과하면 이게 가능해지고, 안 되면 Tuya DP 109 쓰기로 우회한다. **둘 다 막히면 손으로 바꿔야 하므로 유인 시간이 곧 데이터량이 된다** — B3를 먼저 확인해야 하는 이유다.

### 5-3. T7(열화 셀)이 가장 안전하고 재현성 높은 이상 소스다

- 셀 1개를 **반복 사이클링으로 일부러 열화**시킨 뒤 T1과 똑같은 프로토콜을 돌린다.
- 얻는 건 **실제 SOH 저하의 물리적 시그니처**다 — DCIR 상승, 용량 감소, 전압곡선 형태 변화. 인위적 유도가 아니라 진짜 열화다.
- **특별한 안전조치가 필요 없다.** 위험한 실험(T4·T6) 없이도 이상 라벨 데이터를 확보하는 경로다.
- 열화 진행은 시간이 걸리므로 **가장 먼저 시작해 백그라운드로 돌린다.**

### 5-4. 이상 유도 실험 안전 수칙

> ### 🚨 진짜 열폭주는 재현하지 않는다
> 가스 분출·발화를 동반하는 실제 열폭주 시험은 **방폭 챔버·가스 분석·불연 격리 공간**이 전제되는 전문 시험이다. 소규모 랩·실내에서 하지 않는다.
> **AE 학습에는 실제 폭주가 필요 없다** — 정상 분포에서 벗어난 궤적이면 충분하다.

| 실험 | 위험도 | 필수 수칙 |
|---|---|---|
| T7 열화 셀 | 낮음 | 특별 조치 불요 — **이걸 주력으로 쓴다** |
| T5 과방전 | 낮음 | PCM 트립 시 즉시 정지. 트립 반복은 셀 수명을 깎으니 소수 회로 제한 |
| T4 고율 방전 | 중간 | 외부 온도 프로브 실시간 감시, 상한 초과 시 즉시 컷오프. 환기·불연 트레이. **셀 데이터시트 최대 방전 전류 확인 필수** |
| T6 외부 가열 | **중~높음** | **직접 화염·라이터 금지.** 히팅패드/열풍기를 이격시켜 완만히. 상한(80~90°C) 강제 중단. 소화 수단(모래/D급) 비치. **반드시 유인, 환기 확보** |
| 부분 단락 모사 | 높음 | **하지 않는다.** 진짜 단락과 경계가 모호하다 |

**모든 이상 유도 실험은 유인으로만 한다**(§7-2).

### 5-5. DCIR(T2) 해석 시 주의

- **내부저항은 SOC 중간에서 최소, 양 극단에서 증가**하고 **저온에서 전반 상승**한다. 저온+저SOC가 겹치면 증가폭이 비선형적으로 커진다.
- 따라서 **같은 SOC·같은 온도에서만 비교**해야 한다. 절대값 비교는 무의미하고 **동일 조건에서의 추세**로만 쓴다.
- BW150 BRT는 DC 계단전류법이라 AC 임피던스(1kHz)보다 **항상 큰 값**이 나온다. 두 방식의 값을 섞어 비교하지 마라.
- 펄스가 길수록 측정 저항이 커진다(옴 → 전하이동 → 확산 저항이 순차로 포함됨). **BW150 BRT의 정확한 펄스 폭·스텝은 매뉴얼에 없다** — 그래서 절대값의 물리적 의미를 주장하지 말고 추세만 쓴다.

### 5-6. 컷오프 전압을 왜 3.0V로 잡는가

IEC 61960 관행상 18650 종지전압은 **2.75V**가 흔하지만, **우리 셀은 보호회로(PCM)가 있어 그 전에 PCM이 먼저 트립할 수 있다.** 3.0V로 잡고 실측 트립 전압을 확인한 뒤 조정한다.

### 5-7. 공개 데이터셋 병용

NASA(PCoE·Randomized Battery Usage)·Oxford·CALCE 데이터로 **사전학습 → 자체 데이터로 미세조정**하는 경로가 문헌적으로 뒷받침된다(디코더만 재학습하거나 재구성 오차 임계값만 재보정하는 것이 전체 재학습과 동등하거나 낫다는 보고).

이건 `docs/final_month_strategy.md` §2에서 정한 **"공개 데이터셋으로 설계 검증 → 자체 실측으로 학습"** 서사와 정확히 같은 것이며, **출처를 명시해 보고서에 쓴다.**

> 참고: NASA/Oxford/CALCE의 정확한 샘플링 주기는 원문에서 확인하지 못했다(미확인). 다만 배터리 시험기 관행상 정전류 구간 **1~4초 로깅이 표준적**이라, **1초는 이 분야에서 거친 축이 아니다** — 보고서에서 방어 가능한 지점이다.

### 6-2. 반드시 지킬 규약

- **`current_a` 부호는 계약을 따른다 — 양수 = 충전, 음수 = 방전.** BW150은 방전 전용이라 화면에는 부호 없는 양수가 뜬다. **CSV에 쓸 때 음수로 뒤집어라.** 이걸 빠뜨리면 조립 후 INA226 데이터와 합칠 때 방전이 충전으로 학습된다.
- **`test_phase`가 `NORMAL`이 아닌 행은 AI 정상패턴 학습에서 제외한다.** 계단 전류(BRT·P0~P6)와 이상 유도 실험은 사람이 만든 파형이라 정상으로 배우면 실제 이상을 놓친다. 모드 2 스펙의 `diag_phase` 제외 규칙과 같은 이유다.
- **파일 1개 = 세션 1개.** 파일명 `bw150_<battery_id>_<YYYYMMDD-HHMMSS>_<test>.csv`.
- **세션 메타데이터는 별도 사이드카 JSON**에 남긴다 — 셀 ID·정격 용량·시작 SOC·주변 온도·BRT 내부저항 측정값·프로브 부착 위치.

## 7. 무인 수집 안전 수칙

밤새 방전을 돌리려면 **Pi나 PC가 죽어도 배터리가 안전해야 한다.** BW150의 기기 내장 설정이 그 역할을 한다 — 소프트웨어에 의존하지 않는다.

### 7-1. 수집 시작 전 반드시 설정 (매뉴얼 §9 시스템 설정 메뉴)

| 설정 항목 | 값 | 이유 |
|---|---|---|
| `Discharge Cutoff Volt` | **3.0V** (리튬이온 1셀) | 과방전 방지. 소프트웨어가 죽어도 기기가 멈춘다 |
| `Limit Time Discharge` | 예상 소요 + 30분 | 무한 방전 방지 |
| `Over_Temp Ext.T` | **45°C** (초기 보수값) | **셀에 프로브를 붙인 상태여야 의미가 있다** |
| `Over_Temp MOS` | 기본 100°C 유지 | 기기 보호 |
| `Over_Current Protect` | 시험 전류 + 여유 | |

### 7-2. 지켜야 할 것

- **외부 온도 프로브를 반드시 셀에 부착하고 `Over_Temp Ext.T`를 켠다.** 이 프로브가 조립 전 유일한 열 감시 수단이다. 안 붙이고 무인 방치하면 온도 감시가 **0중**이다.
- **`Over_Temp Ext.T` 문턱은 실측으로 조정한다.** 45°C는 시작값일 뿐이며, 정상 방전에서 셀이 얼마나 오르는지 먼저 유인 관찰로 확인하고 그보다 여유를 둔 값으로 내린다.
- **가연물 없는 곳, 불연성 트레이 위에서.** 셀 보호회로(PCM)가 있지만 그것이 유일한 과전류 보호다.
- **첫 세션은 반드시 유인 관찰.** 무인은 같은 조건을 유인으로 최소 1회 완주한 뒤에만.
- **이상 유도 실험(§5)은 절대 무인으로 하지 않는다.**

> ⚠️ **OCP 25A·OPP 150W는 고정 문턱이라 셀 보호에 쓸 수 없다.** 2550mAh 셀에 25A는 이미 파괴적이다. 셀 보호는 위 표의 컷오프 전압·온도 설정과 PCM이 담당한다.

## 8. 조립 후 센서 합류 계획

### 8-1. ⚠️ 두 데이터를 한 모델에 그냥 섞지 마라

BW150 CSV는 **1초**, 조립 후 스트림은 **100ms**다. 30-step 윈도우가 각각 30초·3초를 덮으므로, 라벨만 같을 뿐 **다른 시간 스케일의 데이터**다. 섞어서 한 번에 학습시키면 모델이 두 스케일을 구분 못 해 조용히 망가진다.

세 가지 처리안 중 하나를 골라야 한다:

| 안 | 방법 | 평가 |
|---|---|---|
| **(a) 리샘플 통일 (권장)** | 100ms 스트림을 **1초로 다운샘플**해 BW150 데이터와 같은 축에 놓고 학습 | 데이터가 합쳐져 학습량이 늘어난다. 100ms의 이점을 학습에서는 포기하되, **추론은 100ms 스트림을 1초로 집계해 넣으면 그대로 동작** |
| (b) 사전학습 → 미세조정 | BW150 데이터로 사전학습, 100ms 실측으로 미세조정 | 데이터가 적을 때 유리하나 절차가 늘어난다 |
| (c) 분리 운용 | BW150 데이터는 검증·보고서용으로만, 학습은 100ms 실측만 | 가장 깔끔하지만 조립 전 수집분이 학습에 안 쓰인다 |

**(a)를 권장한다** — 조립이 늦어질수록 BW150 수집분이 유일한 실데이터가 되기 때문이다.

### 8-2. 합류 시 컬럼 매핑

§6-1의 컬럼명을 계약과 맞춰 뒀으므로 합류는 다음만 하면 된다:
1. 100ms 스트림을 1초로 집계 — 전압·전류·전력은 **평균**, 온도는 **최댓값**(피크 보존), `Wh_cumsum`은 마지막 값
2. BW150 CSV의 빈 컬럼(`temp_ir_surface`·`pressure_raw`)은 결측으로 두고, 모델 입력 특징에서 제외하거나 결측 마스크를 준다
3. `temp_contact`의 의미 차이(1점 vs 3점 최댓값)를 사이드카 메타데이터에 기록해 둔다

### 8-3. BW150의 역할 전환

조립 완료 시점에 BW150은 **데이터 소스 → 기준기/부하**로 돌아간다. 그 이후의 정본은 `mode1_backend_spec.md` §12(INA226 대조 검증)다.

## 9. 미확인 항목 — 실기로 확인하며 지운다

기존 스펙의 H1~H9와 같은 성격이다. **BW150을 처음 연결하는 날 B1~B4를 한 번에 소거하라** — 30분이면 끝나고, 여기서 막히면 수집 계획 전체가 바뀐다.
