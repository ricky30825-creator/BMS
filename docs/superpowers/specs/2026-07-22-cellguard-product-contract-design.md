# 셀가드 디자인 무관 제품 계약서(product_contract.md) 설계

## 목적

`설계 산출물/셀가드 프로토타입_v3.html`의 **기능과 유저플로우를 디자인에서 분리해** 문서로 확정한다. 이 문서를 프롬프트에 넣으면 어떤 시각 방향으로도 v3와 동일한 기능·흐름을 갖는 화면을 만들 수 있어야 한다.

이번 작업은 **디자인 방향을 정하지 않는다.** 새 디자인은 사용자가 직접 프롬프트로 진행하며, 이 문서는 그 프롬프트의 입력물이다.

## 배경 — 기존 문서를 그대로 쓸 수 없는 이유

`docs/`에는 이미 기능정의서 2종·유저플로우 2종이 있고 요구사항 108개(REQ-WEB-001~072, 101~136)로 커버리지도 좋다. 그러나 세 가지 문제가 있다.

**1. 기준 파일이 두 세대 뒤처져 있다.**
`feature_definition.md:3`과 `admin_feature_definition.md:3`의 기준 HTML이 `/Users/jungjeahwan/Downloads/셀가드 프로토타입 (standalone).html`(2026-07-10)로 적혀 있다. 이후 v2(07-15), v3(07-22)를 거쳤다.

**2. 그러나 기능 자체의 드리프트는 작다.** 세 버전의 번들 마크업을 실측한 결과:

| 마크업 길이 | 246,066자 | 296,293자 | 298,836자 |
| 라우트 수 | 20 | 20 | 20 |

라우트 20개는 세 버전이 **완전히 동일**하다. state 키 증가분 7개 중 6개(`heroIdx`, `landingTab`, `landingSA/SB/SC`, `landingStatPlayed`)는 랜딩 애니메이션용 표현 상태이고, 기능 추가는 `rawModal`(원본 데이터 조회) 하나뿐이다. **기존 문서는 내용상 대부분 유효하며, 다시 쓸 필요가 없다.**

### 정본 4종의 어휘는 중립화하지 않는다

정본은 "v3가 이랬다"를 정확히 기록해야 하고, v3에는 실제로 모달이 있으니 모달이라 써야 맞다. 형태 어휘를 걷어내는 것은 신규 계약서의 일이다. 두 문서가 서로 다른 일을 하게 해서 모순을 없앤다.

**결과적으로 프롬프트에는 `product_contract.md` 하나만 넣는다.** 따라서 이 문서는 자기완결적이어야 하며, 다른 문서를 읽어야 이해되는 서술을 쓰지 않는다.

## 고정 / 자유 판정표

계약서 맨 앞에 배치한다. 프롬프트를 받는 모델이 가장 먼저 읽는 내용이다.

| | 항목 |
|---|---|
| **자유** | 색·간격·반경·그림자·타이포·모션 / 화면 개수와 경계 / 정보 표시 그릇(모달·시트·인라인·전용 페이지) / 목록 탐색 방식(페이지네이션·무한스크롤·가상스크롤) / 내비게이션 구조 |
| **고정** | 표시해야 할 데이터 항목 / 가능해야 할 동작 / 4단계 상태 등급과 임계 / 안전 게이트와 불변 조건 / 상태·예외 처리 / 반응형 3종(데스크톱·태블릿·모바일) 지원 |

화면 개수·경계가 자유이므로 계약서는 "화면"이 아니라 **기능 영역(surface)** 단위로 쓴다. 한 영역이 새 디자인에서 화면 1개일 수도, 둘로 쪼개질 수도, 다른 영역과 합쳐질 수도 있다.

내비게이션 구조가 자유이므로 REQ-WEB-017(사이드 메뉴 접기)은 계약서에서 삭제하고 "9개 목적지에 도달 가능해야 한다"만 남긴다.

## 계약서 구조

### 블록 A — 공통 헤더 (~80줄)

매 프롬프트에 재투입하는 블록. 다음을 담는다.

1. **질문 규칙** (아래 별도 절)
2. 고정/자유 판정표
3. 4단계 상태 등급과 임계 — 두 스케일을 병기한다. Final Score는 0.0–1.0으로 산출하고 UI에는 0–100 정수로 표시한다.

   | 등급 | Final Score | UI 표시 |
   |---|---|---|
   | 정상 | 0.0–0.3 | 0–29 |
   | 주의 | 0.3–0.6 | 30–59 |
   | 경고 | 0.6–0.8 | 60–79 |
   | 위험 | 0.8–1.0 | 80–100 |
4. 도메인 용어 정의 — 이상점수(Final Score), AE Score, Informer Score, Score Fusion, 측정 모드 1/2/3, `device_id`(측정 장비) vs `battery_id`(측정 대상), Kill-Switch, 인터락, Fail-Safe
5. 금지 목록

**금지 목록** — 자유롭게 두면 실행 모델이 자주 이탈하는 지점이다.

- 4단계 등급의 임계값을 바꾸지 않는다
- 이상점수의 소수 자릿수(0.00 형식)를 바꾸지 않는다
- 안전 게이트를 생략하지 않는다 (재인증·사유 입력 없는 차단 경로를 만들지 않는다)
- 관리자 전용 기능을 일반 사용자 영역에 노출하지 않는다
- 측정 모드 인터락(동시 활성 불가)을 무시하지 않는다
- 이상점수 범례를 3구간(정상 0–39 / 주의 40–69 / 위험 70+)으로 쓰지 않는다 — v3의 버그이며 4등급이 정본이다
- 배터리 미연결 상태에서 잠긴 영역을 열어주지 않는다
- 목업 데이터 부록에 없는 수치를 지어내지 않는다

### 블록 B — 과업 플로우 (~200줄)

"화면 → 화면"이 아니라 과업 단위로 쓴다. 순서와 게이트만 고정하고, 어느 화면에서 수행하는지는 지정하지 않는다.

```markdown
## T2. 측정 시작

1. 저장된 배터리를 확인한다 — 측정 모드로 범위를 좁힐 수 있어야 한다
2. 대상을 선택한다
3. **게이트** — 동시에 하나만 연결 가능함을 알리고 확인을 받는다
4. 측정 세션이 시작되고 실시간 관제 정보에 반영된다

**실패 경로** — 디바이스 오프라인이면 3에서 중단하고 사유를 알린다
**불변** — 게이트 3을 건너뛰는 경로는 존재할 수 없다
**추적** — REQ-WEB-032~034, 039
```

이는 이 레포에서 이미 검증된 방식이다 — 라이트 글래스 리디자인도 g1~g4 그룹별 순차로 실행했다.

## 질문 규칙 — 계약서 맨 앞

새 디자인 실행은 Sonnet이 수행한다. Sonnet은 계약서에 빈칸이 있으면 묻지 않고 그럴듯하게 채운다. 그렇다고 "애매하면 물어봐"라고만 쓰면 색 하나까지 묻거나 아무것도 묻지 않는 두 방향으로 실패한다. **언제 묻고 언제 스스로 결정할지를 갈라줘야 한다.**

**반드시 멈추고 사용자에게 묻는다**
- "고정"으로 적힌 항목인데 내용이 불충분해 그대로 옮길 수 없을 때
- 계약서에 없는 정보나 동작을 추가해야 할 것 같을 때
- 목업 데이터 부록에 없는 값이 필요할 때
- 하려는 디자인이 안전 게이트·불변 조건과 충돌할 때
- 한 영역의 정보량이 많아 쪼개야 하는데 어디서 끊을지 판단이 서지 않을 때

**묻지 말고 스스로 결정한다**
- 판정표의 "자유" 항목 전부

**물을 때의 형식**
- 무엇이 왜 막혔는지 한두 문장 + 선택지 + 잠정 추천
- 답을 받기 전에 그 부분을 추측으로 채워 진행하지 않는다. 대신 답에 의존하지 않는 나머지 작업은 마저 끝내고 질문을 함께 올린다

이 규칙은 `CLAUDE.md`(사용자 전역 지침)의 "막히면 즉시 물어보기"와 동일한 원칙이다.

## 어휘 중립화 규칙

계약서 작성 시 적용한다.

| v3 어휘 | 계약서 표현 |
|---|---|
| 카드로 확인한다 | 다음 항목을 함께 확인한다 |
| 모달을 연다 | 현재 맥락을 잃지 않고 확인·결정한다 |

| 상단 알림 아이콘 | 미확인 알림에 접근한다 |
| 행을 클릭한다 | 개별 항목의 상세를 연다 |

## 추출 방법

계약서는 추측이 아니라 v3 마크업에서 뽑는다.

1. `python3 tools/bundle_io.py unpack`으로 마크업(298,836자 / 2,371줄)을 꺼낸다
2. 라우트별 렌더 구간을 특정하고, 각 구간의 표시 데이터·동작·조건 분기를 나열한다
3. 나열 결과를 기존 REQ-WEB ID와 대조해 **양방향**으로 검사한다
   - 계약서에 있는데 REQ에 없다 → v3 델타이거나 문서 누락
   - REQ에 있는데 v3에 없다 → 문서가 옛 버전을 기술 중
4. 목업 데이터를 부록으로 추출한다

**번들을 손으로 편집하지 않는다.** 이번 작업은 읽기 전용이지만, 202번 줄은 22MB base64 자산 매니페스트이므로 어떤 경우에도 건드리지 않는다.

## 브라우저 검증 결과 (2026-07-22)

v3 번들을 로컬 HTTP 서버(`file://`는 확장이 차단)로 띄워 육안 확인하고, 마크업 grep으로 교차 검증했다. 미해결 2건이 모두 해소됐고 문서에 없던 사실 4건이 추가로 나왔다.

### 1. `devices`(F5)는 도달 불가능한 고아 라우트

- 마크업에 `<!-- ===== DEVICES ===== -->` 섹션(L657–670)이 있고, 화면 타이틀·i18n 라벨·목업 데이터(`devicesList`, L1845)까지 완비돼 있다
- 그러나 `route`를 `'devices'`로 바꾸는 코드가 **0건**이다(`go('devices')`, `setState({route:'devices'})` 모두 없음)
- `userNav` 9개·`adminNav` 5개 어디에도 없다. 로그인 전후 모두 사이드바에 나타나지 않는다

**계약서 처리** — F5를 기능 영역에서 제외한다. 도달 경로가 없는 화면은 유저플로우가 성립하지 않는다. 대신 "미구현 항목" 절에 근거와 함께 기록해, 새 디자인에서 되살릴지 사용자가 판단할 수 있게 한다. 이에 따라 계약서의 기능 영역은 **20개가 아니라 19개**다(F5 결번 유지).

### 2. 모달 인벤토리는 16개

섹션 주석 마커(L1146–1429) 기준으로 확정했다.

| | 모달 | | 모달 |
|---|---|---|---|
| 1 | GENERIC DETAIL | 9 | CSV EXPORT |
| 2 | USER DETAIL (INFO + LOGS) | 10 | PDF EXPORT |
| 3 | USER EDIT | 11 | AUTO KILL-SWITCH |
| 4 | BATTERY DETAIL (STATUS + LOGS) | 12 | CONNECT CONFIRM |
| 5 | NOTICE EDIT / NEW | 13 | EDIT BATTERY |
| 6 | NOTICE ARCHIVE / DELETE CONFIRM | 14 | NEW BATTERY |
| 7 | RAW 데이터 | 15 | RELAY APPROVAL |
| 8 | PASSWORD RESET | 16 | LOGIN |

선행 스펙의 17개 셈과 1개 차이다. 별도 섹션 없이 인라인 렌더되는 오버레이(알림 드롭다운 `notifOpen`, 비교 추가 `compareOpen`, 모드·정렬·상태·역할 드롭다운 4종)는 위 셈에서 제외했다.

### 3. [신규] 배터리 미연결 시 전면 잠금 게이트 — 문서 4종에 0건

```js
const gated = !this.state.isAdmin && !connectedId;
const locked = gated && r !== 'battery';
```

일반 사용자가 배터리를 연결하기 전에는 `battery`를 제외한 **8개 메뉴가 모두 잠긴다.** 잠긴 항목은 클릭해도 아무 일이 없고(`go: () => {}`) 자물쇠 표시가 붙는다. 로그인 직후 도착지도 대시보드가 아니라 배터리 관리이며, "배터리를 연결해야 대시보드·측정 세션·이상 탐지에 접근할 수 있습니다"라는 안내가 뜬다. 관리자(`isAdmin`)는 게이트를 받지 않는다.

이는 제품의 **최상위 진입 게이트**인데 기존 문서 4종에 한 글자도 없다. 계약서 블록 B의 T2 앞단에 `**게이트**`로 명시한다.

### 4. [신규] REQ-WEB-034가 기술한 "이 배터리 측정 버튼"은 v3에 없다

배터리 카드에는 별도 버튼이 없고 **카드 전체가 클릭 대상**이다. 문서가 옛 버전을 기술 중이다. 계약서에는 형태를 빼고 "저장된 배터리 항목에서 측정 대상을 선택할 수 있어야 한다"로 쓴다.

### 5. [신규] 이상점수의 UI 스케일은 0–100 정수다

`CLAUDE.md`와 기존 문서는 0.0–1.0으로 기술하나, v3 화면은 정수 0–100으로 표시한다(게이지 "18", 카드 이상점수 82·58·33·24). 같은 값의 표현 스케일 차이다.

**계약서 처리** — 둘 다 명시한다. "AI가 산출하는 Final Score는 0.0–1.0이며, UI에는 100배한 0–100 정수로 표시한다." 블록 A의 등급표도 두 스케일을 병기한다.

### 6. [신규] v3 내부에 등급 임계 모순이 있다 — 범례가 틀렸다

**판정 로직** (L1647–1650) — 4등급:

```js
let scoreColor = '#16A34A', scoreLabel = '정상';
if (score >= 80) { scoreLabel = '위험'; }
else if (score >= 60) { scoreLabel = '경고'; }
else if (score >= 30) { scoreLabel = '주의'; }
```

정상 0–29 / 주의 30–59 / 경고 60–79 / 위험 80–100 — `CLAUDE.md`의 4등급(0.0–0.3 / 0.3–0.6 / 0.6–0.8 / 0.8–1.0)을 100배한 값과 **정확히 일치**한다.

**게이지 범례 텍스트와 보조 색상 로직** (L1924–1965) — 3구간:

```
정상 0–39   주의 40–69   위험 70+
score >= 70 ? 'danger' : score >= 40 ? 'warn' : 'ok'
```

`경고` 등급이 없고 경계값도 다르다. score 65는 판정 로직으로 "경고"지만 범례로는 "주의 40–69"에 걸린다. score 35는 판정 로직으로 "주의"지만 범례로는 "정상 0–39"다. 목업 데이터(18·24·33·58·82)가 우연히 두 체계에서 같은 결과를 내 화면상 드러나지 않았다.

**계약서 처리** — 판정 로직(4등급)을 정본으로 삼는다. `CLAUDE.md`와 일치하고 내부적으로도 일관되기 때문이다. 범례 3구간은 **v3의 버그**로 기록하고, 새 디자인이 이를 복제하지 않도록 블록 A 금지 목록에 "게이지 범례를 3구간으로 쓰지 않는다"를 추가한다.

## 실행 모델 고려사항

이 스펙의 구현(계약서 작성)은 **추출과 판단이 섞인 작업**이라 실행 모델의 여력이 필요하다. 후속 플랜은 영역 단위로 태스크를 쪼개고, 각 태스크에 원본 마크업의 앵커 문자열을 명시한다. 한 태스크에 여러 영역을 넣지 않는다.
